# 振り返り日報作成スキル

セッションログを一次情報として、カレンダー・Google Docs・Slack・Git logで補強した日報を作成する。

## 🔑 最重要原則: 事実ベースで書く

**ソースに無いことは書かない**。これが他のすべてのルールに優先する。

### 禁止事項
- **でっち上げ禁止**: 「捨てた選択肢」「背景」「決めたこと」をソース無しに**推測で補完しない**
- **婉曲表現禁止**: 「想定」「たぶん」「〜と思われる」「〜のはず」「〜だろう」などの**推測語を本文に書かない**
- **断定禁止**: ソースが無いのに「〜は無かった」「〜のみ」と**断定しない**（例: Slack指摘「特筆すべき無し」は確認できた範囲だけで言う）

### 必須事項
- 各記述項目は**ソースを特定できる**こと（セッションログ / カレンダー / Docs / Slack / Git log のどれか）
- ソースが無い項目は **`_（言及なし）_`** と明記する。書かないか、明示するかの二択で、**穴埋めはしない**
- 推定が必要な箇所（感情など）は **`（推定）`** マークを付ける
- 時刻・人名・数値などの**事実情報はソースの原文をそのまま採用**する（言い換え・要約しない）

### 区別の例
| OK | NG |
|---|---|
| 「`docs/vpc-cidr-expansion.md` を作成」（Writeツール呼び出しで確認可） | 「ドキュメント基盤を整えた」（抽象化しすぎ） |
| 「Slack投稿で `5月中旬目処に進捗報告` と記載」（原文引用） | 「5月中旬を目指す方針で合意したと思われる」（推測） |
| 「明日の予定: カレンダーに登録なし」 | 「明日は 09:30-10:00 想定: ◯◯定例」（想定） |
| 「捨てた選択肢: _（言及なし）_」 | 「捨てた選択肢: 別案も検討したが採用せず」（中身空っぽの埋め草） |

## 設定ファイル

スキル実行前に必ず設定ファイルを読み込む。

`config.jsonc` は `daily-reflection` と `yojitsu-csv` の両スキルから共有されるため、
どちらのスキル内部にも属さないリポジトリ直下の `config/` に置いている。

このスキル自身は2つの経路で呼ばれる（実体は同じ）:

- **リポジトリを開いている場合**: `<リポジトリ>/.claude/skills/daily-reflection/`
- **他のディレクトリの場合**: `~/.claude/skills/daily-reflection/`（リポジトリへのシンボリックリンク）

スキルディレクトリの特定には `SKILL.md` の存在を使う（`config` はスキル外に出たため、
その存在を目印には使えない）。どちらから呼ばれても動くよう、**存在する方を使う**:

```bash
for d in ./.claude/skills/daily-reflection ~/.claude/skills/daily-reflection; do
  [ -f "$d/SKILL.md" ] && SKILL_DIR="$d" && break
done
SKILL_DIR_REAL="$(cd "$SKILL_DIR" && pwd -P)"
REPO_ROOT="$(cd "$SKILL_DIR_REAL/../../.." && pwd -P)"
cat "$REPO_ROOT/config/config.jsonc"
```

⚠️ `config.jsonc` は JSONC（コメント付きJSON）。`//` で始まる行はコメントなので、値として解釈しないこと。

以降このドキュメントで `{skill_dir}` と書いた箇所は、ここで解決したパスを指す。

`config.jsonc` から以下の値を取得して使用する:
- `sources.calendar.id`: GoogleカレンダーID
- `sources.calendar.display_name`: カレンダー上の表示名。この名前のカレンダーの予定を主対象とする
- `sources.calendar.ignore_calendars`: 無視するカレンダー名の配列（工数入力用など日報に不要なカレンダーを除外する）
- `sources.slack.user_id`: SlackユーザーID
- `sources.git.author`: `git log --author` に渡す値。メールアドレスを推奨（詳細は後述のGit log収集の節を参照）
- `output_dirs.report`: 日報の出力先ディレクトリ
- `output_dirs.timesheet`: 稼働実績の出力先ディレクトリ。`output_dirs.report` とは独立した設定
- `projects`: cwdパス → プロジェクト名のマッピング。キーは絶対パスか `~/...`（相対パスは無効）。
  1ディレクトリ1活動が原則だが、これは推定の既定値であり、実際の作業内容が明らかに違う場合は個別に判断する。
  そのリポジトリに関係する作業（スキル改善等も含む）は同じ活動、全く別の作業やグローバル設定の変更は別の活動として扱う
- `work_codes`: 案件番号・作業コード・作業名称の一覧。稼働時間テーブルのプロジェクト名と作業コードの対応に使用する。
  **日報・稼働実績のプロジェクト名には `display_name` を使う**（`work_name` は工数システムの正式名称で長いため）。
  `display_name` が未設定のコードは `work_name` を使うが、表記が揺れる原因になるので設定を促す

### 出力先パス（`output_dirs.*`）の解決ルール

`output_dirs.report` / `output_dirs.timesheet` の値は、書き方によって解決の仕方が変わる:

- `{REPO_ROOT}` で始まる場合: このリポジトリのルート基準で解決する
- `~` で始まる場合: ホームディレクトリに展開する
- `/` で始まる絶対パスの場合: そのまま使う

**上記3種類以外の書き方はエラーにする。** `./outputs/...` のような裸の相対パスは受け付けない。
`./` は一般に cwd 基準を意味するため、リポジトリルート基準という独自解釈を持たせると読み手が誤解する。
リポジトリ内に出力したい場合は `{REPO_ROOT}/outputs/...` と明示的に書く。

**cwd（Claude Code を起動したディレクトリ）基準では絶対に解決しないこと。** `setup.sh` でグローバルに使えるようにした後、
別ディレクトリから `/daily-reflection` を実行すると cwd はリポジトリと無関係な場所になるため、cwd 基準で解決すると
意図しない場所に日報・稼働実績が出力されてしまう。裸の相対パスを黙って解決せずエラーにするのは、
設定ミスを出力先の事故ではなく起動時のエラーとして気付けるようにするため。

`REPO_ROOT` は上の「設定ファイル」節で既に求めているので、ここでは再度求めない。

```bash
# プレースホルダはパターンとしても除去対象としても使うため変数に入れる
# （case のパターン中で '{REPO_ROOT}' をクォートすると展開されないため）
REPO_ROOT_PH='{REPO_ROOT}'

resolve_output_dir() {
  local raw="$1"
  case "$raw" in
    "$REPO_ROOT_PH"*) echo "$REPO_ROOT${raw#"$REPO_ROOT_PH"}" ;;  # リポジトリルート基準
    ~*)               eval echo "$raw" ;;                          # ホームディレクトリに展開
    /*)               echo "$raw" ;;                               # 絶対パスはそのまま
    *)
      echo "ERROR: 出力先パスは {REPO_ROOT}/... | ~/... | /... のいずれかで書く: $raw" >&2
      return 1
      ;;
  esac
}

REPORT_DIR="$(resolve_output_dir "<config.output_dirs.report>")" || exit 1
TIMESHEET_DIR="$(resolve_output_dir "<config.output_dirs.timesheet>")" || exit 1
```

`|| exit 1` を付けているのは、コマンド置換への代入は関数が `return 1` しても
それ自体は失敗扱いにならず、**空の出力先で処理が続いてしまう**ため。
パスが解決できない場合は日報を書き始める前に止め、設定の誤りをユーザーに伝える。

以降このドキュメントおよび [format.md](format.md) で `{output_dirs.report}` / `{output_dirs.timesheet}` と書いた箇所は、
ここで解決した `$REPORT_DIR` / `$TIMESHEET_DIR` を指す。

## ステップ

### 全体方針: 時系列チャンク処理

**全情報を一括収集してから日報を組み立てるのではなく、時系列に沿って1〜2時間単位のチャンクごとに情報収集→確認を繰り返す。**

これにより:
- コンテキスト圧縮による再読み込みを防ぐ（チャンクごとに処理が完結する）
- ユーザーの確認が軽くなる（「この1時間はこうでしたよね？」だけ答えればよい）
- 空白時間を自然に検出できる（チャンク間のギャップがそのまま空白）

### 1. 骨格の構築（確認不要・自動実行）

設定ファイルを読み込み（上の「設定ファイル」の手順で `$SKILL_DIR` を解決する）、
`date` コマンドで今日の日付と曜日を取得する。対象日は**今日**。

以下を**並列で**取得し、1日の骨格（タイムスロット一覧）を作る:

**a) セッションログの一覧と時系列の把握**

セッションログは JSONL（1行1エントリのJSON）。

**対象日のログ:**
```bash
ls ~/.claude/daily-logs/<対象日>/
```

1行目が `{"type":"session","id":"...","cwd":"...","started":"..."}` 形式のメタ情報。
文字列パース不要で `cwd` と `started`（セッション開始時刻、ISO8601+タイムゾーン）がそのまま取れる。

```bash
head -1 ~/.claude/daily-logs/<対象日>/<ファイル名>.jsonl | jq .
```

2行目以降が時系列のエントリ。`role`（user/assistant）、`text`（発言）、`tool`/`target`（ツール呼び出し）を持つ。
`ts` は日付を含むISO8601なので、日跨ぎの判定にヘッダ行の特別なパースは不要（後述）。

```bash
# ツール呼び出しだけ機械的に絞り込む例
jq -c 'select(.tool)' ~/.claude/daily-logs/<対象日>/<ファイル名>.jsonl
```

**⚠️ 日跨ぎセッションの検出（必須）:**

セッションログはSessionEndフック実行時に**セッション開始日**のディレクトリに保存される。そのため、前日以前に開始されたセッションが対象日まで継続していた場合、対象日のディレクトリには存在しない。

各エントリの `ts` に日付が含まれるため、前日・前々日のログを開いて `ts` を見るだけで対象日の活動かどうかを判定できる:
```bash
# 前日・前々日のセッションログのうち、対象日のtsを含むものを検索
grep -l "<対象日>" ~/.claude/daily-logs/<前日>/*.jsonl ~/.claude/daily-logs/<前々日>/*.jsonl 2>/dev/null
```
→ ヒットしたファイルの中から `.ts` が `<対象日>` のエントリだけを `jq` 等で抽出して使う

⚠️ **重要: ファイル名のタイムスタンプはセッションのエクスポート（保存）時刻であり、作業開始時刻ではない。**（セッション開始時刻は1行目の `started` から取る）
- 1つのセッションに数時間分の作業が含まれることがある
- 複数のセッションログが近い時刻（例: 17:24, 17:25, 17:37）に集中していても、実際の作業は時間的に分散している
- **実際の作業時系列は、セッションログの中身（引き継ぎノートのタイムスタンプ、ユーザー発言、ツール呼び出し内容）から再構成する**
- Slackの投稿時刻も作業時系列の裏付けに使える

**b) Googleカレンダー（今日 + 明日）**
```
mcp__claude_ai_Google_Calendar__list_events(
  calendarId="<config.sources.calendar.id>",
  timeMin="<今日>T00:00:00+09:00",
  timeMax="<今日>T23:59:59+09:00",
  timeZone="Asia/Tokyo"
)
```
明日分も同様に取得する。

- `{config.sources.calendar.display_name}` のカレンダーの予定を主対象とする
- `{config.sources.calendar.ignore_calendars}` に列挙されたカレンダーは無視する
- `attendees[]` の `responseStatus` でフィルタ:

| responseStatus | 扱い |
|---|---|
| `accepted` / `tentative` | **含める** |
| 自分がオーガナイザー（organizer.self == true） | **含める** |
| `declined` | **除外** |
| `needsAction`（未応答） | **後でチャンク確認時にまとめて聞く** |
| 自分が `attendees` に含まれない | **除外** |

**c) 前日の日報**
```
{config.output_dirs.report}/<昨日のYYYY>/<昨日のMM>/<昨日>.md
```
→ 「明日やること」セクションを抽出（持ち越しTODO突合用）

**骨格の組み立て:**

⚠️ **骨格構築時にセッションログの中身を必ず確認する。** ファイル名の時刻だけで時系列を組まない。
- 各セッションログの冒頭〜数十行を読み、**実際に何時頃の作業か**を把握する
- 同一cwd の引き継ぎノート（`.claude/handovers/`）があれば、そのタイムスタンプも参照して作業の区切りを特定する
- **作業終了時刻は最後のセッションログの内容（最後のユーザー発言やツール呼び出し）から判断する**。引き継ぎノートのファイル名時刻は使わない

カレンダー予定とセッション内容を時系列で並べ、**1〜2時間単位のチャンク**に分割する。
チャンクの区切りは打ち合わせの前後や、作業内容の切れ目など自然な区切りに合わせる。

### 2. チャンクごとの処理（時系列順に繰り返す）

各チャンクについて以下を実行する:

#### 2a. チャンクの情報収集

**そのチャンクに必要な情報だけを読み込む:**

- **セッションログ**: 該当時間帯のセッションログを読み込み、以下を抽出:
  - 何をしたか（ツール呼び出しで裏付けられるもののみ）
  - 何を決めたか / 捨てた選択肢 / 背景
  - 翌日のTODO
  - **未マッピングのcwd**: ディレクトリ名から推定し、チャンク確認時にまとめて聞く。承認されたら `config/config.jsonc` に自動追記
- **Slack**: 該当時間帯の発言・Backlog Bot通知を検索
  ```
  mcp__claude_ai_Slack__slack_search_public_and_private(
    query="from:<@{config.sources.slack.user_id}> after:<チャンク開始> before:<チャンク終了>",
    sort="timestamp", sort_dir="asc", limit=20
  )
  ```
  - `from:` だけでなく、プロジェクトチャンネル内の全投稿（他メンバーからの言及含む）も確認
  - Backlog Bot通知はテキストが空で返る場合があるが、**通知の存在と時刻**はエビデンスとして使える
  - 作業時間と投稿時間はずれることがある。該当チャンク内で見つからなければ前後に範囲を広げる
- **Google Docs**: チャンク内に打ち合わせがあり、Docsリンクがあれば取得
  ```
  mcp__claude_ai_Google_Drive__read_file_content(file_id="<DocsのID>")
  ```
  - 人名・固有名詞は文字起こしに誤字が多い。カレンダーの`attendees[]`、Slack検索、過去の日報で裏取りする。裏取りできなければ `【表記要確認】` マーク
- **Git log**: チャンク内にセッションがあったリポジトリのみ
  ```bash
  git -C <cwd> log --author="<config.sources.git.author>" --since="<チャンク開始>" --until="<チャンク終了>" --oneline --name-only
  ```
  - `--author` はメールアドレスで指定する。author 名（表示名）はリポジトリごとに異なることがあるが、メールアドレスは共通のことが多いため。`git log --author` は部分一致検索なので、メールアドレスを渡せば表示名が何であってもヒットする

#### ⚠️ 日付境界バリデーション
- セッションログ内の「昨日」「先週」等の時間表現は"言及"であり"今日の作業"ではない
- **ツール呼び出し**（Bash/Read/Edit/Write 等）に対応しない記述は日報に書かない

#### 2b. チャンクの確認（ユーザーに提示）

収集した情報をもとに、**そのチャンクのタイムライン + 要約**を提示し確認する:

```
【09:00-11:00】
- 09:10-09:50 A案件: 検証環境コスト一覧作成
- 09:50-11:00 A案件: チケット差分更新 + 定例アジェンダ作成
- その他: B案件Slack(10:30)
→ これで合っていますか？
```

**時刻の丸めルール:**
- タイムラインの時刻は **5分単位に丸める**（例: 09:11→09:10、17:27→17:30）
- ピンポイントの正確さより可読性を優先

**Slack のタイムライン表示ルール:**
- そのチャンクの主作業に関連するSlack投稿はタイムラインに含める
- **関連性が薄いピンポイントの連絡**（別プロジェクトの単発Slack等）は個別行にせず **「その他」行にまとめる**

**隙間時間の扱い:**
- タスク間の短い空白（5〜20分程度）は**直後のタスクに含める**。ユーザーに「何をしていましたか？」と聞かない
- 裏で準備・思考・移動をしている可能性があり、いちいち確認するのは煩わしい
- 30分以上の空白のみ確認する

**確認時にまとめて聞くこと:**
- 30分以上の空白時間があれば「XX:XX-XX:XX は何をしていましたか？」
- needsAction のカレンダー予定があれば「この会議は出席しましたか？」
- 未マッピングのcwdがあれば「このプロジェクト名は○○でよいですか？」

ユーザーの回答を反映したら次のチャンクへ進む。

### 3. 日報の組み立て

全チャンクの確認が完了したら、[format.md](format.md) のフォーマットに従い日報を組み立てる。

**統合のルール:**
- **事実ベース原則を遵守**（冒頭の「🔑 最重要原則」を参照）。ソースに無いことは書かない
- セッションログが最優先。カレンダー・Slack・Git log・Google Docsは補強・裏付け
- ただし**打ち合わせ内容**は Google Docs（文字起こし）と Slack（議事録投稿）の方が詳細なことが多い
- 同じプロジェクトの複数セッションは、タスク単位で論理的にまとめる（セッション単位ではない）
- 自由記述欄はプレースホルダーとして残す
- 参加表明していないカレンダー予定は除外
- 明日の予定はカレンダー確認分のみ。**`（カレンダー登録なし）`** で補完しない
- 同時間帯に作業と打ち合わせがある場合は `🔀 並行` マーク
- 前日の「明日やること」と照合し、消化できなかった項目は **「持ち越しTODO」** セクションに記載

### 4. ファイルに保存

全チャンクは確認済みなので、最終確認は**自由記述欄に何か書きたいことがあるか**だけ聞く（日報側は事実ベースでチャンク確認済みのため、これ以外の追加確認は不要）。

確認後、以下の順で保存する。

1. **日報を保存**する（ディレクトリが存在しない場合は `mkdir -p` で作成する）:
   ```
   {config.output_dirs.report}/YYYY/MM/YYYY-MM-DD.md
   ```
2. 稼働実績を保存する前に、[format.md](format.md) の**整合性チェック**（`total_minutes` = 各 entry の `minutes` の和、各 entry の `breakdown[].minutes` の和 = その entry の `minutes`、など）を必ず実行する。
3. **稼働実績を保存**する（ディレクトリが存在しない場合は `mkdir -p` で作成する）。稼働実績の宛先は人間ではなく工数入力システムなので、**JSON で保存する**:
   ```
   {config.output_dirs.timesheet}/YYYY/MM/YYYY-MM-DD.json
   ```
4. 両方の保存が終わったら、保存した JSON を**その場でテーブルに整形して画面に提示する**（ファイルには書かない、Claude の応答として表示するだけ）。提示後、「修正したい箇所があれば教えてください」と伝える。

**確認フローは「一旦保存してから修正」**であることに注意する。保存前に「これでいいですか？」と聞いて待つのではなく、先に両方保存してから提示する。ユーザーが何も言わなければそれで完了、修正指示があればJSONファイルを直す。

### API呼び出しの注意事項

- **過剰並列によるAPI 529 (Overloaded) を避ける**: 同時並列は最大4本まで。Drive の Docs 取得は最大3件並列
- **失敗時**: 5秒待って1回リトライ。それでも失敗なら `_（取得失敗）_` と明記して先に進む
- **Slack検索の日付範囲**: 前日〜翌日を基本。当日で見つからなければ範囲を広げる

# 日報フォーマット

## 出力ファイル

日報と稼働実績は性質が異なるため、別ファイルに分けて出力する。

| ファイル | 保存先 | 性質 |
|---|---|---|
| 日報 | `{output_dirs.report}/YYYY/MM/YYYY-MM-DD.md`（例: `2026/06/2026-06-04.md`） | 事実の記録。保存したら基本触らないアーカイブ |
| 稼働実績 | `{output_dirs.timesheet}/YYYY/MM/YYYY-MM-DD.json`（例: `2026/06/2026-06-04.json`） | 申告値。工数入力システムへの登録に使う機械可読データ。人間向けにはファイル保存後に画面上でテーブルに整形して提示する |

`output_dirs.report` と `output_dirs.timesheet` はそれぞれ独立した設定値。同じディレクトリに設定されていれば同じ場所に保存される。
どちらもディレクトリが存在しない場合は作成する。

稼働実績の宛先は人間ではなく工数入力システム（および `yojitsu-csv` スキルによるCSV変換）であるため、
**JSON で保存する**。ユーザーへの確認は、保存後にJSONをテーブルに整形して画面に提示することで行う。

## 日報の構造

```markdown
---
date: YYYY-MM-DD
day: {曜日}
office: {remote | office | hybrid | unknown}  # 出社形態。確実な情報源（カレンダー/Slack）が無ければ unknown
projects: [{プロジェクト名1}, {プロジェクト名2}, ...]
meetings_count: {数値}
---
```

## 稼働実績の構造

稼働実績は **JSON** で保存する（機械可読データとして、工数入力システムや `yojitsu-csv` スキルが直接読み取れるようにするため）。日報側との対応は `date` フィールドで取れる（日報と稼働実績は同じ `YYYY-MM-DD` を使うので、ファイル名を揃えれば突合できる。リンクの埋め込みは不要）。

```json
{
  "date": "YYYY-MM-DD",
  "day": "{曜日}",
  "total_minutes": {合計・分単位の整数},
  "entries": [
    {
      "case_number": "{案件番号}",
      "customer": "{顧客名}",
      "code": "{作業コード}",
      "work_name": "{作業名称}",
      "project": "{日報上のプロジェクト名}",
      "minutes": {このプロジェクトの稼働時間・分単位の整数},
      "breakdown": [
        { "activity": "{活動名}", "minutes": {所要時間・分単位の整数} }
      ]
    }
  ]
}
```

フィールドの説明:
- `date` / `day`: 日報と同じ日付・曜日
- `total_minutes`: 合計。**分単位の整数**（`1h30m` のような文字列ではなく `90`）。計算・検証を確実にするため
- `entries[]`: プロジェクト（≒作業コード）単位の行。日報の稼働時間テーブルの1行に対応
  - `case_number` / `code` / `work_name` / `customer`: `config/config.jsonc` の `work_codes` を参照して埋める
  - `project`: 日報上のプロジェクト名。`work_codes[].display_name` を使う（`config.projects` の値と同じ文字列になる）。
    `display_name` 未設定のコードは `work_name` で代用するが、日によって表記が揺れないよう同じ日報内・日をまたいでも同一表記を保つ
  - `minutes`: このプロジェクトの稼働時間。分単位の整数
  - `breakdown[]`: 備考の内訳。各要素が活動名（`activity`）と所要時間（`minutes`、分単位の整数）を持つ

> 作業コードは `config/config.jsonc` を参照する。日報のプロジェクト名と作業コードの対応が不明な場合はユーザーに確認する。

> ### 合計の算出（絶対値）
> **`total_minutes` = 勤務終了時刻 - 勤務開始時刻 - 1h（固定昼休憩） - 追加休憩（中抜け等）**
> - 勤務開始 = Slack開店時刻 or タイムライン最初のブロック開始時刻
> - 勤務終了 = Slack閉店時刻 or タイムライン最後のブロック終了時刻
> - 固定昼休憩は常に1h。追加休憩はカレンダーやSlackで明示された中抜け等のみ差し引く
> - **セッションログやSlackに記録がない時間帯でも、明示的な休憩でなければ稼働時間に含める**（対面での会話・ドキュメント確認・思考等の非デジタル作業がある）
> - `total_minutes` は**15分単位に丸めた分数**にする（例: 8時間 → `480`）
>
> ### プロジェクト別の配分
> `total_minutes` を絶対値として確定した上で、タイムラインの活動ブロックを参考に `entries[]` としてプロジェクトごとに配分する。
> - 各 `entries[].minutes` は**15分単位に丸める**（例: 50分→`60`、1時間25分→`90`）
> - **各 `entries[].minutes` の合計 = `total_minutes`** になること
> - **各 `entries[].breakdown[].minutes` の合計 = その entry の `minutes`** になること
> - タイムラインは5分単位の細かさで構わないが、`entries[].minutes` と `breakdown[].minutes` は必ず15分単位（15の倍数）にする
> - プロジェクトに紐付かない活動（日報作成、社内申請、勉強会等）は「コンサル部」の entry にまとめ、`breakdown` に内訳を記載する
> - **ブログ執筆**（DevelopersIO記事準備、hands-onリポジトリ作成等）は「コンサル部」とは別に「ブログ」の entry として記載する。ブログ作業がない日はこの entry を省略する
>
> ### 整合性チェック（稼働実績保存前に必ず実行）
> 1. `total_minutes` = 勤務終了 - 勤務開始 - 1h - 追加休憩 であること
> 2. 各 `entries[].minutes` の合計 = `total_minutes` であること
> 3. 各 `entries[].breakdown[].minutes` の合計 = その entry の `minutes` であること（15の倍数であることも確認）
> 4. タイムラインに30分以上の空白がないこと（あればチャンク確認時に必ずユーザーに確認済みであること）

## ルール

### 事実ベース原則（最重要）
- ソースに無いことは書かない。必ず `_（言及なし）_` か `_（取得失敗）_` で明示する
- 推定情報には `（推定）` マークを付ける
- 「想定」「たぶん」「〜と思われる」等の婉曲・推測表現は本文に書かない
- 「特筆無し」のような断定はしない（「確認した範囲では」と限定する）

### タイムライン
- **セッションログのファイル名はエクスポート時刻であり、作業開始時刻ではない**。実際の作業時系列はセッション内容・引き継ぎノート・Slackから再構成する
- 打ち合わせはカレンダーの時刻をそのまま使う
- 時刻は **5分単位に丸める**（例: 09:11→09:10、17:27→17:30）
- **時間重複** がある場合は `🔀 並行` 行で両方を記載する（隠さない）
- 打ち合わせ中の内職は、タイムライン上は打ち合わせのみ表示し、作業はプロジェクト詳細で記載
- 関連性の薄いピンポイントのSlack連絡は個別行にせず「その他」行にまとめる

### プロジェクトセクション
- プロジェクト単位でグループ化
- タスクの粒度はセッション単位ではなく、論理的なまとまりで区切る
- **捨てた選択肢 / 背景**: ソースに比較検討の形跡が無ければ `_（言及なし）_` と書く（推測で埋めない）

#### 見出しと正式名称の書き分け
見出しには短い名前（`work_codes[].display_name`）を使い、その直下に引用形式で
案件の正式名称（`work_codes[].work_name`）を添える。

```markdown
## プロジェクト: ACMEポータル刷新
> 株式会社ACME_会員ポータル刷新（2026年4-9月）
```

- 見出しを短くするのは、タイムラインの表・frontmatter の `projects` と同じ文字列を使うため。
  正式名称は40文字を超えることがあり、表に入れると崩れる
- 正式名称を併記するのは、予実管理CSVに出るのが `work_name` であり、日報とCSVの突合を可能にするため。
  また案件名には契約期間（例: `（2026年4-9月）`）が含まれることがあり、更新で変わりうる。
  見出しを `display_name` で固定しておけば、期間が変わっても過去日報と同じ名前で追える
- `display_name` が未設定のコードは見出しにも `work_name` を使い、引用の併記は省略する（重複するため）
- 正式名称が取れない場合（`work_codes` に該当コードが無い等）は引用行を省略する
### 打ち合わせ
- Googleカレンダーから取得し、参加表明（responseStatus: accepted / tentative / オーガナイザー）したものだけ記載
- 未応答（needsAction）はユーザーに事前確認、不参加（declined）は除外
- セッションログ・Google Docs（Geminiメモ）・Slackで関連する議論があれば補足

### 明日の予定
- カレンダーで確認できた予定のみ記載
- 確認できない時間帯は `（カレンダー登録なし）` と書く
- 不確かな情報は書かない

### 自由記述
- プレースホルダーとして残し、スキルでは埋めない
